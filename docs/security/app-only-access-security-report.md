# Security Report — App-Only (Tenant-Wide) Access

**Product:** `@checkfirst/nestjs-outlook` — Microsoft Graph integration module
**Audience:** Enterprise security / IT administrators evaluating consent
**Scope:** The "app-only" (OAuth 2.0 client-credentials) access mode used to read/write
Outlook calendars and mail on behalf of an organization's users.
**Date:** 2026-07-29

---

## 1. Executive summary

This application integrates with Microsoft 365 to schedule and synchronize calendar (and
optionally mail) events for your users. It supports a **tenant-wide "app-only" access mode**,
in which **one authorized administrator grants consent once** instead of every employee
clicking through an individual consent screen.

Key assurances for a security-conscious administrator:

- **You are always in control of the grant.** Access requires an **explicit admin-consent
  action by a Microsoft 365 Global Administrator** in your own tenant. No end user can enable
  it by "clicking a random button," and the app cannot self-authorize. The grant is visible,
  auditable, and revocable from your Entra ID (Azure AD) admin center at any time.
- **You decide the blast radius, not us.** By default an app-only grant can reach every
  mailbox in the tenant, so the app is designed to be **scoped down by you** to a single
  security group using Microsoft's native Application Access Policy / RBAC for Applications.
  Access is then managed purely by group membership on your side. (Section 6.)
- **Strong, phishing-resistant credentials.** Production deployments authenticate with an
  **X.509 certificate** (RSA-PSS / PS256 signed JWT assertion). The private key never leaves
  the app's server and is never transmitted to Microsoft or logged. (Section 4.)
- **Least-privilege permission set.** The integration requests three Graph application
  permissions — calendar, mail (optional), and directory read — and no more. (Section 5.)
- **Webhooks are authenticated.** Inbound change notifications are verified against a
  per-subscription secret and rejected if forged. (Section 7.)

The remainder of this document describes exactly what is requested, how credentials are
handled, and the controls you retain.

---

## 2. What "app-only" access means

Microsoft Graph offers two authentication models. This app supports both, kept in **separate,
independent code paths** (documented decision: DR-006, "Dual Authentication Architecture"):

| | Delegated (per-user) | **App-only (tenant-wide)** |
|---|---|---|
| Who consents | Each individual user | **A single admin, once** |
| Who the app acts as | The signed-in user | The application, on behalf of users |
| Reach | That one user's data | Users in tenant (scopable — see §6) |
| Credential | User OAuth token | App certificate / secret |

App-only mode exists because enterprise customers asked to onboard many employees without
each one completing an individual OAuth flow. It uses the industry-standard **OAuth 2.0 client
credentials grant** — the same mechanism Microsoft documents for daemon/background services.

---

## 3. The consent flow — who authorizes what, and how it is revoked

Access is **not** granted by an end user clicking a button. The flow is:

1. The app operator supplies you with an **admin-consent URL** for your tenant
   (`https://login.microsoftonline.com/{your-tenant}/adminconsent?...`). This is generated by
   `AppOnlyAuthService.getAdminConsentUrl()`.
2. **A Global Administrator in *your* tenant** opens that URL, authenticates with your
   credentials/MFA, and is shown Microsoft's standard consent screen **listing the exact
   permissions requested** (Section 5). Nothing is granted until your admin clicks **Accept**.
3. Microsoft redirects back with confirmation; the app records that your tenant is connected
   (`admin_consent=True`). The app **cannot** fabricate this — the confirmation comes from
   Microsoft, and the callback only *activates* a tenant record you have pre-registered.

**Revocation is entirely in your hands and is immediate.** At any time your admin can revoke
the grant from **Entra ID → Enterprise applications → [this app] → Permissions → Revoke
admin consent**, or disable/delete the enterprise application. Once revoked, the app's tokens
stop working (Microsoft rejects them); the app surfaces this as a `NEEDS_ADMIN` health state
rather than silently retrying.

> Reference: `docs/how-to/connect-enterprise-tenant.md`,
> `src/services/auth/app-only-auth.service.ts` (`getAdminConsentUrl`, `handleAdminConsentCallback`).

## 4. Credential handling — how the app proves its identity

Two credential types are supported, with **certificates strongly preferred and taking
precedence** (documented decision: DR-007, "Certificate Authentication").

### Certificate authentication (recommended, production default)

- The app builds a short-lived **JWT client assertion** and signs it with an RSA private key
  using **PS256 (RSA-PSS with SHA-256)** — a modern, strong signing algorithm. The certificate
  is identified to Microsoft via the `x5t#S256` (SHA-256 thumbprint) header.
- The signed assertion is valid for **10 minutes maximum**, carries a random `jti` to prevent
  replay, and is generated fresh per token request.
- **The private key never leaves your server and is never sent to Microsoft.** Only the
  signature crosses the network; Microsoft verifies it with the public key you registered.
- **The key is never logged.** The module accepts the key as a value loaded by *your* host app
  from secure storage (environment variable, secrets manager, or mounted secret) and does not
  write it to logs or error messages. On failure it logs only Microsoft's diagnostic
  identifiers (AADSTS codes, trace/correlation IDs), never credentials.

Why this matters to you: even if network traffic were intercepted, the captured assertion
expires in minutes and cannot be reused to mint new tokens without the private key — unlike a
shared secret, which grants indefinite impersonation if leaked.

### Client secret (fallback, non-production)

A traditional client secret is supported for simpler setups but is explicitly documented as the
**less secure** option, to be rotated manually. Enterprise deployments should mandate the
certificate path (and can enforce this by simply not issuing a secret).

### Access-token lifecycle

- Tokens returned by Microsoft are valid ~1 hour and are **cached in process memory only**,
  refreshed ~5 minutes before expiry. **Access tokens are not written to disk or database.**
- In multi-container deployments each instance fetches its own token; there is no shared token
  store to compromise.

> Reference: `src/services/auth/app-only-auth.service.ts` (JWT signing, PS256, caching);
> DR-007 security considerations.

## 5. Exactly what permissions are requested (least privilege)

The app-only grant requests the **Microsoft Graph *Application* permissions** below and no
others. These are what your admin will see and approve on the consent screen:

| Permission | Type | Why it is needed |
|---|---|---|
| `Calendars.ReadWrite` | Application | Create/read/update the scheduling events this product manages |
| `Mail.ReadWrite` | Application | Only if you enable email features; omit if unused |
| `User.Read.All` | Application | Resolve your internal user IDs to the correct Microsoft mailbox (directory read) |

Notes for your review:

- The token requests the `.default` scope, which means **"exactly the permissions the admin
  already consented to"** — it cannot silently expand beyond what you approved on the consent
  screen.
- `Mail.ReadWrite` is only required if you use the email features; a calendar-only deployment
  does not need it. Request the minimum set for your use case.
- If you want the app to only *see* users it has been explicitly told about (rather than being
  able to enumerate the directory), `User.Read.All` can be downgraded to `User.ReadBasic.All`,
  or replaced entirely by the app resolving users only via explicitly-mapped email addresses
  (Section 6).

> Reference: `docs/how-to/connect-enterprise-tenant.md` (Prerequisites),
> `docs/how-to/restrict-app-access-to-a-group.md`.

## 6. Confining the app to a subset of users (the key enterprise control)

This is the most important control for a cautious administrator. An app-only grant *by default*
can reach every mailbox in the tenant. The app is explicitly designed to be **scoped down by
you** using **Microsoft-native, tenant-side controls** — the restriction is enforced by
Microsoft, not by trusting the app:

- **Application Access Policy** (Exchange Online): your Exchange admin creates a mail-enabled
  security group of allowed users and binds this app (by its client ID) to it with
  `-AccessRight RestrictAccess`. The app can then touch **only** members of that group; access
  for anyone else returns `403` at Microsoft. You manage access thereafter purely by adding or
  removing people from the group — no involvement from the app operator.
- **RBAC for Applications** (Microsoft's newer, recommended model): assign the app a role such
  as `Application Calendars.ReadWrite` **scoped to a security group** or administrative unit.

Under such a policy, calls for out-of-scope users fail cleanly with `403`, which the app
already treats as a permanent "user not in scope" outcome (not a retryable error).

**Important boundary to be aware of:** these mailbox policies scope Exchange data
(calendar/mail). They do **not** by themselves restrict the *directory-read* permission
(`User.Read.All`). To also limit which users the app can *enumerate*, use `User.ReadBasic.All`,
administrative units, or have the app look users up only by the specific emails you map to it.
This is documented transparently.

> Reference: `docs/how-to/restrict-app-access-to-a-group.md`.

**Recommendation for your deployment:** grant consent, then immediately apply an Application
Access Policy / RBAC scope limiting the app to a dedicated security group before mapping any
users. This gives you a hard, admin-managed boundary regardless of app behavior.

## 7. Webhooks (change notifications) security

The app subscribes to Microsoft Graph change notifications so it can react to calendar changes.
Because webhook endpoints must be publicly reachable, they are protected against forgery
(documented decision: DR-002):

- Each subscription is created with a **unique, unguessable `clientState` secret** (a random
  UUID bound to the user/tenant). Microsoft echoes it back on every notification.
- An inbound-notification guard validates `clientState` **per item** against the stored value.
  Anything missing, referencing an unknown subscription, or mismatched is **rejected and not
  processed**, and surfaced as an observable `WEBHOOK_REJECTED` security event.
- The design **fails closed**: a subscription without a verifiable stored `clientState` is
  rejected rather than trusted. The app refuses to persist a subscription with an empty
  `clientState`.

Result: a forged notification from an internet attacker cannot drive the app to act, because it
cannot produce the correct secret.

> Reference: `src/guards/webhook-client-state.guard.ts`,
> `src/services/subscription/microsoft-subscription.service.ts`, DR-002.

## 8. Data handling summary

| Item | Where it lives | Notes |
|---|---|---|
| App private key / secret | Provided by host from secure storage | Never logged, never sent to Microsoft (cert) |
| Graph access tokens | In-process memory cache only | Not persisted to DB/disk; ~1h TTL |
| Tenant registration | `microsoft_tenants` table | Tenant GUID, client ID, cert thumbprint, consent timestamp, status |
| User mappings | `microsoft_users` table | Your user ID ↔ Microsoft user ID / UPN |
| Webhook `clientState` | Subscription record | Per-subscription secret for notification verification |

The app stores identifiers and mappings needed to operate; it does not create a secondary
long-term store of your users' mailbox contents as part of this auth mechanism.

## 9. Residual considerations & recommendations

Honest notes so your team can make an informed decision:

1. **App-only is powerful by default** — an unscoped grant can access all mailboxes. **Mitigation
   (recommended):** apply an Application Access Policy / RBAC group scope immediately after
   consent (Section 6). This is the single most impactful control you hold.
2. **Certificate expiry is the host's responsibility.** The app does not validate the
   certificate's own expiry date; ensure your key-rotation process covers it. Microsoft supports
   multiple certificates per app registration for zero-downtime rotation.
3. **Directory read is broader than mailbox scope.** If minimizing directory visibility matters,
   downgrade to `User.ReadBasic.All` or use mapped-email lookups (Section 5–6).
4. **Prefer certificate over client secret** and decline to provision a client secret if you
   want to enforce this at the tenant level.
5. **Audit and monitor.** The grant is visible in Entra ID Enterprise Applications; sign-in and
   audit logs record token issuance under the app's identity, and the app emits
   `WEBHOOK_REJECTED` / user-health events you can monitor.

---

## 10. Checklist for granting consent safely

- [ ] Confirm the requested permissions match Section 5 (and drop `Mail.ReadWrite` if unused).
- [ ] Require **certificate** authentication; do not issue a client secret.
- [ ] Have a Global Administrator (not an end user) perform the consent from the provided URL.
- [ ] Immediately apply an **Application Access Policy / RBAC scope** limiting the app to a
      dedicated security group.
- [ ] Decide on directory-read scope (`User.Read.All` vs `User.ReadBasic.All` vs mapped-email).
- [ ] Verify scope with `Test-ApplicationAccessPolicy` for an in-group and out-of-group user.
- [ ] Record where the private key is stored and the rotation schedule.
- [ ] Confirm the revocation procedure (Entra ID → Enterprise applications → Revoke consent).
